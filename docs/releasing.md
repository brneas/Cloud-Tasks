# Build and publish a release

This guide prepares a signed Cloud Tasks APK for direct installation and an
optional public GitHub Release. Google Play is not required.

The final Android identity is:

| Setting | Value |
| --- | --- |
| Application ID | `org.tecdesigns.cloud_tasks` |
| Android namespace | `org.tecdesigns.cloud_tasks` |
| Launcher name | `Cloud Tasks` |
| Release version | `1.0.0+20` |

The application ID and signing certificate together identify an installed
Android app. Keep both stable for every future update.

## 1. Finalize the Android project

The public Git tag used to build an APK must include the configured `android/`
directory and `pubspec.lock`. A release cannot be reproduced from the Dart
files alone.

For a new platform directory, run this once from the project root:

```powershell
flutter create --platforms=android --org org.tecdesigns .
```

For an existing Android directory, verify these values instead of recreating
it:

1. In `android/app/build.gradle.kts`, set both `namespace` and `applicationId`
   to `org.tecdesigns.cloud_tasks`.
2. Set the first line of `MainActivity.kt` to
   `package org.tecdesigns.cloud_tasks`.
3. Move that file to
   `android/app/src/main/kotlin/org/tecdesigns/cloud_tasks/MainActivity.kt`.
4. In `android/app/src/main/AndroidManifest.xml`, set the application label to
   `Cloud Tasks`.
5. Complete every permission, receiver, desugaring, and backup setting in
   [Android setup](android-notifications.md).
6. Run `dart run flutter_launcher_icons` and visually inspect the icon.

If a debug build with this same application ID is already installed, Android
will not replace it with a differently signed release build. Synchronize all
pending changes first, then uninstall the debug build before installing the
first release build. Later releases will update in place when they use the same
release key and a higher build number.

## 2. Create and protect the release key

For direct APK distribution, this is the **app signing key**, not a disposable
Play Store upload key. Losing it prevents updates to every existing install;
disclosing it lets someone produce an APK Android accepts as your app.

Create it outside the repository. `keytool` prompts for passwords, so they do
not appear in shell history:

```powershell
keytool -genkey -v `
  -keystore "$env:USERPROFILE\.android\cloud-tasks-release.jks" `
  -storetype JKS -keyalg RSA -keysize 2048 -validity 10000 `
  -alias cloud-tasks
```

Create `android/key.properties` locally:

```properties
storePassword=REPLACE_WITH_THE_KEYSTORE_PASSWORD
keyPassword=REPLACE_WITH_THE_KEY_PASSWORD
keyAlias=cloud-tasks
storeFile=C:\\Users\\YOUR_NAME\\.android\\cloud-tasks-release.jks
```

Both `android/key.properties` and common keystore extensions are ignored by
this repository. Confirm that before committing:

```powershell
git check-ignore -v android/key.properties
Test-Path "$env:USERPROFILE\.android\cloud-tasks-release.jks"
```

The keystore path should exist outside the repository. Never copy it into the
project.

At the top of `android/app/build.gradle.kts`, place the imports before the
existing `plugins` block. Place the property-loading code immediately after
that block:

```kotlin
import java.io.FileInputStream
import java.util.Properties

plugins {
    // Keep the plugins generated by Flutter here.
}

val keystoreProperties = Properties()
val keystorePropertiesFile = rootProject.file("key.properties")
if (keystorePropertiesFile.exists()) {
    keystoreProperties.load(FileInputStream(keystorePropertiesFile))
}
```

Inside its `android` block, add the release signing configuration before
`buildTypes` and assign it to the release build:

```kotlin
signingConfigs {
    create("release") {
        keyAlias = keystoreProperties.getProperty("keyAlias")
        keyPassword = keystoreProperties.getProperty("keyPassword")
        storeFile = keystoreProperties.getProperty("storeFile")?.let { file(it) }
        storePassword = keystoreProperties.getProperty("storePassword")
    }
}

buildTypes {
    release {
        signingConfig = signingConfigs.getByName("release")
    }
}
```

Compare the result with Flutter's current
[Android signing guide](https://docs.flutter.dev/deployment/android). The
release block must not retain `signingConfigs.getByName("debug")`.

Keep two encrypted backups of the keystore and its passwords in separate
locations. Record the certificate fingerprint for future release comparison:

```powershell
keytool -list -v `
  -keystore "$env:USERPROFILE\.android\cloud-tasks-release.jks" `
  -alias cloud-tasks
```

The certificate fingerprint is public information; publish it with the first
release and compare it for every update. The keystore and its passwords remain
secret.

Do not publish the keystore, passwords, `key.properties`, or an unredacted
terminal transcript.

## 3. Audit the public source tree

Review the exact files and history that will be pushed:

```powershell
git status --short
git ls-files
git log --oneline --decorate --all
git grep -n -I -E "(password|secret|token|api[_-]?key|PRIVATE KEY)"
```

Matches in test fixtures and documentation still require human review. Also
check that these are absent from `git ls-files`:

- `android/key.properties`, `local.properties`, `.env` files
- keystores, private keys, APKs, AABs, databases, exports, and logs
- real Nextcloud URLs, usernames, app passwords, and task data

Generated plugin registration must not be tracked. Check it explicitly:

```powershell
git ls-files | Select-String "GeneratedPluginRegistrant.java"
```

If that prints a path, remove only that generated file from the index with
`git rm --cached PATH_FROM_THE_COMMAND`, then run `flutter clean` and
`flutter pub get`. Never fix plugin-registration failures by editing the Java
file.

Deleting a secret in the latest commit does not remove it from Git history. If
a real credential was ever committed, revoke or rotate it first, then remove
it from every affected commit before publishing.

## 4. Validate a clean release candidate

Run the complete suite from a clean working tree:

```powershell
flutter doctor -v
flutter clean
flutter pub get
flutter pub outdated
flutter pub deps --style=compact
dart run flutter_launcher_icons
dart format --set-exit-if-changed .
flutter analyze
flutter test
git status --short
```

Complete [the release checklist](release-checklist.md) against a real
Nextcloud account. In particular, verify rapid completion, offline recovery,
manual ordering in both directions, reminders, background sync, sharing, and
an upgrade from the previous installed build.

Inspect `pubspec.lock` and every changed direct or transitive dependency. Commit
the lockfile so the tag resolves the versions that were tested.

## 5. Build and verify APKs

For the simplest public download, build one universal APK:

```powershell
flutter build apk --release
```

Its default path is `build/app/outputs/flutter-apk/app-release.apk`. It is
larger, but users do not need to know their device architecture.

For a smaller APK for a Pixel or another modern 64-bit ARM device:

```powershell
flutter build apk --release --split-per-abi
```

Use `build/app/outputs/flutter-apk/app-arm64-v8a-release.apk` on the Pixel. If
publishing split APKs, label each architecture clearly.

Verify the signature with Android SDK Build Tools'
[`apksigner`](https://developer.android.com/tools/apksigner):

```powershell
apksigner verify --verbose --print-certs `
  build/app/outputs/flutter-apk/app-release.apk
```

The reported certificate must match the fingerprint recorded in step 2. Then
create a SHA-256 checksum:

```powershell
Get-FileHash -Algorithm SHA256 `
  build/app/outputs/flutter-apk/app-release.apk
```

Rename the artifact before publishing, for example
`Cloud-Tasks-v1.0.0-universal.apk`, and save its checksum in
`SHA256SUMS.txt`. Save the `apksigner --print-certs` output in
`SIGNING-CERTIFICATE.txt`. Do not commit release binaries to the Git repository.

Install the exact release artifact on the target phone and repeat a short smoke
test:

```powershell
adb install -r .\Cloud-Tasks-v1.0.0-universal.apk
```

Confirm login, sync, manual order, task editing, notification permission,
background sync, restart recovery, import/export, and disconnect. Test the APK
itself, not only a debug build from `flutter run`.

## 6. Publish the GitHub repository and release

1. Commit the configured Android project, `pubspec.lock`, source, tests, docs,
   icon assets, complete `LICENSE`, `SECURITY.md`, and `CONTRIBUTING.md`.
2. Push to a private repository while doing one final file and history review.
   Enable the dependency graph, Dependabot alerts, and branch protection where
   the account plan permits. Wait for the validation workflow to pass.
3. Tag the exact tested commit:

   ```powershell
   git tag -a v1.0.0 -m "Cloud Tasks 1.0.0"
   git push origin main --follow-tags
   ```

4. Make the repository public. Immediately enable GitHub
   [secret scanning and push protection](https://docs.github.com/en/code-security/getting-started/quickstart-for-securing-your-repository)
   and
   [private vulnerability reporting](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/configure-for-a-repository).
   Review the initial security scan before announcing or attaching a binary.
5. Protect the default branch and require the validation workflow for future
   merges if that was not available while the repository was private.
6. Create a
   [GitHub Release](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)
   from `v1.0.0`. Paste the contents of
   `release-notes-1.0.0.md` and attach the signed APK,
   `SHA256SUMS.txt`, and `SIGNING-CERTIFICATE.txt`.
7. Verify the uploaded APK's hash after downloading it from the release page.

GitHub automatically provides source archives for the tag. Keeping the tag,
lockfile, Android build configuration, GPL license, and APK together gives
users a clear path to audit or rebuild the release.

## 7. Ship future updates safely

- Keep `org.tecdesigns.cloud_tasks` unchanged.
- Sign every update with the same release key.
- Increase the build number after `+` in `pubspec.yaml` for every distributed
  APK, even when the visible version stays the same.
- Repeat the clean build, signature, checksum, device, and Nextcloud checks.
- Publish from a new immutable Git tag and retain prior releases.

Never replace an existing Git tag or silently replace an uploaded APK. Publish
a new version so users can verify what changed.
